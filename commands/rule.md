Добавь в плагин правило: $ARGUMENTS

Правило должно попасть в исходники плагина, а не в файл загруженной копии. Ничего не записывай до «ок».

1. Рабочая копия: прочитай `DEVFLOW_SRC` из `~/.claude/devflow/.env` (нет ключа — `~/dev/devflow`). Проверь:
```bash
SRC=$(python3 "${CLAUDE_PLUGIN_ROOT}/hooks/lib_env.py" src)
[ -f "$SRC/.claude-plugin/plugin.json" ] && git -C "$SRC" rev-parse --is-inside-work-tree >/dev/null 2>&1 && echo "SRC=$SRC $(git -C "$SRC" status --short | wc -l | tr -d ' ') незакоммиченных" || echo "НЕТ РАБОЧЕЙ КОПИИ: $SRC"
```
Нет копии — остановись: попроси путь к клону репозитория плагина и запиши его в `DEVFLOW_SRC` в `.env`. Незакоммиченные файлы есть — покажи `git status --short` и остановись: `release.sh` требует чистого дерева.

2. Уровень правила — по смыслу текста, один из:
   - поведение в любом проекте (общение, git, проверки, отчёт, тикеты) → `$SRC/rules/general.md`, секция по теме, строка-императив с меткой `[слово]` (или `[хук]`, если правило уже ловит хук плагина);
   - шаг процесса тикета → `$SRC/skills/task-workflow/references/<режим>.md` (new-ticket, start, implement, finish, fixes, show, estimate, status, epics, worktree, brief) или `$SRC/skills/branch-ops/references/<операция|protocol>.md` для операций с ветками, `$SRC/skills/resolve-pr-comments/SKILL.md`, `$SRC/skills/review-pr/SKILL.md`;
   - что проверять в коде на ревью → `$SRC/agents/quality-reviewer.md`, общий чек-лист (новый пункт с номером);
   - механика (нужно ловить хуком) → предложи, какой хук и тест, но код пиши только после отдельного «ок»; версия тогда `minor`;
   - правило про конкретный проект (стек, ветка, команда) → в плагин не кладётся: предложи `.claude/workflow.md` или проектный `CLAUDE.md` этого проекта и остановись.

   Прочитай целевой файл, найди место и сверься, нет ли там уже такого правила. Есть — скажи и остановись.

3. Покажи: файл, после какой строки, точную формулировку (императив, одна-две строки, без «почему» длиннее одного предложения). Жди «ок».

4. Примени правку в `$SRC` (Edit по абсолютному пути) и выпусти версию:
```bash
"$SRC/tools/release.sh" patch "<суть правила в 5–8 словах>" <путь файла относительно $SRC>
```
Скрипт сам прогоняет `tools/check.sh` и тесты, поднимает версию, пишет CHANGELOG и коммитит. Красный `check.sh` — покажи вывод, правку не откатывай, останься на незакоммиченном состоянии и спроси.

5. Обнови установленную копию на этой машине (плагин ставится копией в `~/.claude/plugins/cache`, без этого новая сессия увидит старую версию):
```bash
claude plugin update devflow@devflow
```
   Отчёт: новая версия, файл и строка, последняя строка `git log --oneline -1`. Напомни: правило действует с новой сессии; на других машинах — `git pull` в клоне и `claude plugin update devflow@devflow`. У репозитория плагина есть remote на GitHub: релиз лежит в локальной ветке, пуш — только по команде пользователя, сам не предлагай.

# epics — многотикетные эпики

Эпик — тема, которая раскладывается на несколько тикетов (и, возможно, мелкие подзадачи без тикета). Реестр — `<epics_dir>/README.md`. Каждый эпик:

```
<epics_dir>/<name>/
  README.md     цель, контекст, статус, «Базовая ветка» (если есть)
  design.md     решения эпик-уровня + «Риски и открытые вопросы» (не обязателен)
  tasks.md      нумерованная декомпозиция N.M, статус/ссылка по каждому пункту
  reports/      notes.md, report-N.md — для подзадачи N без отдельного тикета
  tickets/<KEY>/  подзадача, которая ведётся как обычный тикет
```

## Новый эпик

Триггер: «новый эпик <name>».

1. Не сказано — спросить цель, контекст, есть ли декомпозиция.
2. `README.md` (цель, контекст, «в работе, 0 подзадач готово»). Архитектурно значимый — ещё `design.md` тем же процессом, что architectural-тикет.
3. Строка в `<epics_dir>/README.md`.
4. `tasks.md` — сразу, если декомпозиция известна; иначе по ходу.

## Базовая ветка эпика

Если PR тикетов эпика идут в release-ветку эпика, а не в `base`, — она записывается в README эпика (секция «Базовая ветка») и в «Эпик-ветки» `workflow.md`. Все новые тикеты эпика отводятся от неё (`start.md`).

## Тикет эпика: вход

Каждый заход в тикет эпика (new-ticket, start, fixes, research — в том числе первый, когда каталога `tickets/<KEY>/` ещё нет) начинается с чтения, до трекера и кода:

1. `README.md` эпика — цель, «Базовая ветка», «Общие решения».
2. Раздел своего ключа в `tasks.md` эпика целиком, включая блоки **«Передано из <KEY>»** — это требования и риски, которые закрытые тикеты эпика оставили этому.
3. Хвост `reports/notes.md` эпика — строки со своим ключом.

Каждый пункт «Передано из …» в `spec.md` получает явную судьбу: в критерии/сценарии, «вне тикета — куда и почему» (с согласия пользователя) или «уже сделано — где». Молча пропущенный пункт — дефект постановки; в чат summary new-ticket — строкой «Передано из соседних тикетов: N пунктов, из них в работе M».

## Тикет эпика: выход — передача соседям

Всё, что тикет оставляет другому тикету эпика (риск, отложенное требование, «доделать в X»), при `finish` записывается **в раздел адресата** в `tasks.md` эпика — блоком:

```markdown
**Передано из <KEY> — прочитать до постановки** (подробности: `tickets/<KEY>/report.md`):

1. <суть словами бизнеса, пример последствия> Код: `<класс::метод>`.
```

Один блок на источник; повторный `finish` того же тикета — обновить свой блок, не добавлять второй. Адресата нет в `tasks.md` (будущий этап без тикета) — пункт в раздел этапа или в «Риски и открытые вопросы» `design.md` эпика. Строка в своём `report.md` («Передать дальше») и в `reports/notes.md` эпика — дополнительно, не вместо: новая сессия адресата читает свой раздел `tasks.md`, а не отчёты соседей.

## Подзадача без тикета

Мелкая инфраструктурная работа — не заводить тикет искусственно: `reports/report-N.md` эпика, N — номер из `tasks.md` эпика.

## Статус эпика

Триггер: «что по статусу <эпик>», «как дела с <эпик>». README + `tasks.md`: что готово / в работе / не начато, ссылки на report/тикет. Коротко, без деталей закрытых пунктов.

## Список эпиков

Триггер: «какие эпики есть». Вывести `<epics_dir>/README.md` как есть.

## Неясно, часть ли тикет эпика

Не гадать по номеру или названию — спросить. Положить файлы не туда дороже одного вопроса.

# start — «добро» → ветка и план

1. **Базовая ветка.** `base` из конфига, либо базовая ветка эпика, если тикет из эпика и она записана в `<epics_dir>/<эпик>/README.md` (секция «Базовая ветка»):

```bash
BASE=<base или ветка эпика>
git fetch origin "$BASE"
```

Тикет **жёстко зависит** от кода другого тикета, который ещё на ревью и не влит в базу — тогда отводиться от ветки того тикета (цепочка PR). Это осознанное решение, не умолчание: сначала проверить, что нужного кода в базе нет (`git log origin/$BASE`, `git merge-base --is-ancestor <KEY2> origin/$BASE`), и подтвердить у пользователя.

Признак, что у эпика база есть, но не записана: в `base` нет кода уже закрытых подзадач эпика, а их ветки не влиты — спросить пользователя и дописать в README эпика.

2. **Ветка.**
   - Пользователь уже в ветке `<KEY>` — работать в ней, новый воркtree не заводить.
   - Ветка `<KEY>` есть локально — переключиться, не пересоздавать. Нет `spec.md` — восстановить задним числом (из `git log <KEY>` и тикета), пометить в файле, что восстановлен.
   - Ветки нет — `git checkout -b <KEY> origin/$BASE`.
   - Работа параллельно другому тикету — воркtree по `worktree.md`.

3. **Ресёрч по коду → размер:**
   - **small** — 1–2 места, ясный флоу, нет развилок. `tasks.md` из одного-двух пунктов. Реализация в сессии → wip-коммит → один `devflow:quality-reviewer` → сценарий из `spec.md` проверить самому (тест или запрос к локальному стеку) → `finish` без black-box.
   - **bounded** — один модуль или несколько соседних, нет новых решений. `tasks.md`, реализация в сессии, `devflow:quality-reviewer` после каждого пункта, black-box в `finish`.
   - **architectural** — новая подсистема, несколько независимых модулей, развилки. `design.md` → `superpowers:writing-plans` с сохранением в `<KEY>/plan.md` → `implement.md`.

   Размер решает ресёрч, а не часы в трекере. Неожиданная сложность по ходу — остановиться и сказать; размер только растёт. Итог — строкой `Размер: small|bounded|architectural` в `spec.md` после `Статус:` (эту строку читают маппер и Stop-хук циклов; предварительную отметку из new-ticket заменить).

3а. **Карта области — всегда, до `tasks.md`/`design.md`.** `devflow:system-mapper` с брифом (`brief.md`): первая строка `режим: area`, `spec.md`, предполагаемые модули, `architecture_dir` из секции «База знаний» конфига. Выход — карты затронутых модулей в `<architecture_dir>` (созданы или сверены, строка `сверено` на HEAD) и `<KEY>/map.md`; small — одна цепочка и «было → стало», карту модуля только сверить. Карта модуля больше лимита агента (1200 слов или длиннее кода модуля — размер в его ответе) — вернуть мапперу на сжатие через SendMessage, пользователю не показывать. `map.md` показать пользователю в чат целиком: это его понимание системы до кода, не артефакт для агентов. Гейт пуша (`knowledge-base-check.py`) потребует карт по всем файлам ветки и `map.md` — без этого шага finish упрётся в него.

4. **small/bounded** → `<KEY>/tasks.md`:

```markdown
# <KEY>: <summary> — задачи

- [ ] 1. <короткое название подзадачи>
  Образец: <путь существующего класса того же типа> · паттерн: <имя | не нужен — почему> · слой: <слой deptrac или аналога>
```

Каждый пункт — отдельный критерий приёмки из `spec.md` или отдельный затронутый модуль/эндпоинт, а не порядок мыслей. Строка «Образец» — у пункта, который заводит новый класс или компонент: образец найти до записи пункта (как для блока «Паттерны и образцы» в п. 5), путь уходит в бриф реализации эталоном того же типа (`brief.md`); ревьюер сверяет с ней размещение класса. Пункт только правит существующее — строки нет. Отмечать `- [x]` по ходу. `design.md` не создавать.

5. **architectural** → `<KEY>/design.md`:

```markdown
# <KEY>: решения

## Принятые решения

1. <решение> — потому что <основание: код `файл:строка`, цитата первоисточника с разделом или решение пользователя>

## Домен и API

## Контракт API

| Ручка | Случай | Код | Тело ответа | Основание |
|---|---|---|---|---|

## Impact по компонентам

## DTO и интерфейсы

## Паттерны и образцы в проекте

| Новый компонент | Паттерн или «не нужен — почему» | Образец в проекте (путь) | Слой |
|---|---|---|---|

## Было → стало

## Сколько запросов делает решение, где риск N+1

## Риски и trade-offs
```

Блоки обязательны и заполняются именами: сущности и поля с типами, внутренние API, компоненты с тем, что в каждом меняется, DTO и интерфейсы, паттерны с образцами, риски с ценой. После записи — `devflow:spec-critic` с первой строкой брифа `режим: design` (бриф: `spec.md`, `design.md`, `<KEY>/map.md`, пути карт модулей, отчёт `reports/design-critique.md`): пустой блок или общие слова — находка до плана. Без этого вызова Stop-хук блокирует ход (`cycles.md`, агент `spec-critic#режим:\s*design`) `[хук]`; пока нет `reports/design-critique.md`, `design-critique-gate.py` отклоняет запись `plan.md` и вызов implementer по тикету `[хук]` — отложить критику «до первой задачи» нельзя, её находки меняют план.

«Принятые решения» — нумерованный список, пункт с начала строки «1.» или «Р1.» (вложенные подпункты — с отступом): номер решения указывает отчёт fact-checker. Решение, посылку которого проверка опровергла или назвала толкованием, закрывается по колонке «кто решает» отчёта: `источник`, `образец`, `умолчание` — оркестратор исправляет решение по ответу из пруфа сам и дописывает строку `Исправлено по проверке (ГГГГ-ММ-ДД): <что стало>`; `пользователь` — вопрос пользователю (опровержение, цитата, варианты, рекомендуемый первым), его ответ — строкой `Решение пользователя (ГГГГ-ММ-ДД): «его слова дословно»`. Без нужной строки `design-critique-gate.py` не зовёт implementer `[хук]`. Пользователю не выносится то, на что есть источник, образец или умолчание.

«Контракт API» — строка на каждый исход каждой новой или изменённой ручки, включая ошибки и недоступность внешней стороны: код, тело ответа, основание. Основание выбирается по порядку, первое найденное: образец в проекте — путь ручки, которая уже так отвечает в том же случае (ошибка соседнего провайдера, та же валидация); стандарт, прямо называющий этот случай, — цитата с разделом; умолчание ниже; решение пользователя с датой — только когда случай не покрыт ничем из этого. Вывод из цитаты, которого в ней нет дословно, — толкование, не основание. API не меняется — строка «API не меняется».

Умолчания контракта, когда образца в проекте нет и стандарт случай прямо не называет: внешняя зависимость ответила ошибкой 5xx или ответ не разобрать — 502; не ответила вовремя или нет соединения — 504; не хватает нашей настройки (ключи, креды) — 500 с отправкой в трекер ошибок; запрос клиента не прошёл проверку — 422; нет прав или сессия внешней стороны отклонена — 403; лимит — 429. Тело ошибки — формат соседних ручек проекта.

«Паттерны и образцы в проекте» — строка на каждый новый класс или компонент из «Impact по компонентам»: паттерн (Use Case/Action, Strategy, Adapter/Gateway, Template Method, Repository…) или «не нужен» с причиной; существующий класс проекта того же типа, взятый за образец, путём; слой по `deptrac.yaml` или аналогу из проектного `CLAUDE.md`. Образец ищется до записи блока: слои из `CLAUDE.md` и конфига границ, затем grep по суффиксу и роли (`*Action`, `*Handler`, `*Gateway`, интерфейсы-хуки). Переходный каталог вне слоёв — только когда образца в слоях нет, и это пишется в строке. Развилка поведения внутри общего сценария (один вход ведёт себя иначе на шаге) решается паттерном из этого блока, а не замыканием или перестановкой шагов; замыкание без строки «паттерн не нужен — почему» — находка критика.

«Было → стало» — перенос из `map.md` маппера (activity с подсветкой изменённых переходов, изменения сущностей и API), маппер второй раз не вызывать.

   **Критик на каждое решение.** Каждое решение, попадающее в «Принятые решения», до записи проходит `devflow:decision-critic` (`brief.md`: утверждение «делаем X, потому что Y», автор — пользователь или оркестратор, что проверено, карты — `<KEY>/map.md` и карты затронутых модулей; `reports/critic-N.md`). Решение о размещении или структуре класса формулируется с образцом и слоем: «кладём X в <слой> по образцу <путь>, потому что …». Несущую находку критика проверь по коду сам — критик ошибается сопоставимо; пересказ пользователю сверь с отчётом; вердикт — пользователю до того, как решение закрепилось в файле. `BLOCK` без ответа пользователя в `design.md` не записывается.

затем `superpowers:writing-plans` с `spec.md` + `design.md` как спецификацией и явным указанием сохранить план в `<KEY>/plan.md` (не в `docs/superpowers/plans/`). `tasks.md` не создаётся — реализация идёт по задачам `plan.md`.

6. Короткое summary плана — в чат, и сразу к реализации (`implement.md`): повторного гейта нет. Если ресёрч вскрыл риск, не покрытый постановкой, — остановиться и спросить, план молча не расширять.

## Тикет внутри эпика

Файлы тикета — в `<epics_dir>/<эпик>/tickets/<KEY>/` вместо `<tasks_dir>/<KEY>/`, пункт в `tasks.md` эпика получает ссылку на `tickets/<KEY>/`. После завершения — отметить пункт эпика и обновить строки статуса в README эпика и в `<epics_dir>/README.md` (см. `epics.md`).

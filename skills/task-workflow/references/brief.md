# brief — бриф сабагента

Минимальный скелет любого брифа:

- **задача** — что сделать, границы;
- **репозиторий** — абсолютный путь к рабочему каталогу (worktree или вложенный репозиторий), из которого выполнять git и команды проекта;
- **каталог тикета** — абсолютный путь и что читать: `plan.md` §задача N (или пункт `tasks.md`), `design.md` §Принятые решения, хвост `reports/notes.md`; сабагент читает первоисточник сам, пересказ дороже и теряет детали;
- **затрагиваемые файлы**;
- **критерий готовности**; для `implementer` — ещё мутация на каждый новый тест сценария приёмки (сломать проверяемое условие → тест красный → вернуть), итог в отчёте;
- **формат ответа** — «по разделу „Отчёт“ агента»;
- для `implementer` — **обязательные правила** (ниже); путь карты модуля (`<architecture_dir>/<модуль>.md`) и путь эталонного класса того же типа (из строки «Образец» пункта `tasks.md` или блока «Паттерны и образцы» `design.md`, иначе из `CLAUDE.md` проекта) с требованием открыть их, вызывающих и тесты до первой правки;
- для `quality-reviewer` — `режим:`, SHA или диапазон литералом, путь файла отчёта `reports/review-N-rM.md`, на повторе — путь прошлого отчёта; в architectural — раздел «Открыто до правки» из ответа implementer дословно (вход п. 26);
- для `security-reviewer` и `db-reviewer` — режим или диапазон литералом, путь файла отчёта (`reports/security-review.md`, `reports/db-review.md`);
- для `spec-critic` — путь к `spec.md` и файл отчёта `reports/spec-critique.md`; пути карт модулей области из `<architecture_dir>` (есть — перечислить; нет — строка «карт модулей нет»), в режиме design — первая строка `режим: design` (её ищет Stop-хук), ещё пути `design.md`, `<KEY>/map.md` и отчёт `reports/design-critique.md`;
- для `fact-checker` — пути `spec.md`, `design.md` и отчёт `reports/fact-check.md`;
- для `system-mapper` — первая строка `режим: area|feature|troubleshooting`; `architecture_dir` из секции «База знаний» конфига; вход по режиму: area — `spec.md` и предполагаемые модули, feature — `spec.md` и диапазон диффа литералом (`origin/<база>...HEAD`), troubleshooting — путь карты модуля и симптомы из `spec.md`/бага; пути выходов (`<KEY>/map.md`, `reports/feature-map.md`). Правила кода мапперу не передаются: он читает код, не пишет.

Проверяющим ролям (`quality-reviewer`, `security-reviewer`, `db-reviewer`, `black-box-tester`, `fact-checker`, `spec-critic`) правила кода не передаются — только предмет проверки: что проверять, по какому чек-листу, откуда брать вход. `black-box-tester` правила прямо мешают: он не должен знать реализацию. Первая строка брифа `black-box-tester` — `режим: coverage` или `режим: execute`; вход — `spec.md`, `MANUAL_TESTING.md`, стенд из конфига; отчёт implementer, `report-N.md` и `review-N.md` в бриф не вкладывать (мандат «докажи, что сломано» ломается чужими проверками); на повторном раунде — sha новой ревизии и путь прошлого `reports/test-report.md` для строки динамики.

## Бриф `decision-critic`

Критик работает в чистом контексте: переписку не получает, бриф — весь его вход. Четыре поля, без любого он останавливается:

1. **тикет или спека** — путь к `spec.md` (и `design.md`);
2. **утверждение** одной фразой в форме операции: «делаем X, потому что Y» или «причина бага — X, потому что Z» — без «потому что» критик вернёт бриф;
3. **автор** — пользователь / оркестратор / автор PR;
4. **что уже проверено** — команды и результаты, которыми утверждение обосновано.

Плюс путь отчёта `reports/critic-N.md` (N — сквозной номер в тикете) и **карты, если есть** (поле не обязательное): путь `<KEY>/map.md` после start и пути карт модулей `<architecture_dir>/<модуль>.md`, которых касается утверждение; нет карт — строка «карт нет», критик идёт по коду. Не вкладывать: аргументы «за», переписку, своё мнение о вердикте. Вердикт `CONTINUE` / `REVISE` / `BLOCK` — первой строкой ответа; несущую находку оркестратор сверяет по коду сам и доносит пользователю до того, как решение закрепилось в файле.

## «Обязательные правила» для implementer

Собираются скриптом, не по памяти и не на глаз: в T-2122 ручной блок пропустил три правила, и все три дефекта прошли в код.

```bash
python3 "$DEVFLOW_ROOT/skills/task-workflow/scripts/brief-rules.py" "$PWD"
```

Вывод вставляется в бриф целиком, с последней строкой-маркером `<!-- brief-rules v… -->`: implementer проверяет маркер и без него не начинает. Скрипт печатает только то, чего сабагент не получит сам: §0 и правила `[ревьюер]`/`[слово]` проектного `CLAUDE.md` (в worktree читает из основного репозитория), карту «Ревью» и секцию «Миграции» из `workflow.md`, правило ожидания долгих команд. Правила кода берутся из `CLAUDE.md`, в «Ревью» только ссылки и заметки. Общие правила плагина (`rules/general.md`) в бриф не копируются — их сабагент получает хуком SubagentStart; правила `[хук]`/`[линтер]` ловит механика.

Поверх вывода скрипта оркестратор добавляет руками только то, что требует суждения:

1. Из карты «Ревью» — какие файлы правил относятся к файлам задачи (отметить «к этой задаче: …»).
2. Уроки из памяти проекта, ещё не перенесённые в `CLAUDE.md`, если относятся к задаче.

# implement — реализация

Состав ролей — по размеру из `start.md`.

## small и bounded

Реализация в этой сессии, без сабагента-реализатора. По каждому пункту `tasks.md`:

1. Реализовать; новый класс — по образцу из строки «Образец» пункта (открыть его до первой правки, положить в тот же слой); точечные тесты `tests_targeted`.
2. Закоммитить до ревью — `git status --short`, в коммит только файлы тикета, явными путями, SHA сразу в `tasks.md` (переменные shell между вызовами Bash не живут):

```bash
git add <пути> && git commit -m "wip(<KEY>): <пункт>" && git rev-parse --short HEAD
```

`- [ ] N. … (wip: <sha>)`.

3. `devflow:quality-reviewer` с брифом (`brief.md`): `режим: subtask`, SHA литералом, файл отчёта `reports/review-N-r1.md`. Critical/Important — починить, новый коммит (SHA дописать в `tasks.md`), повторный раунд по открытым находкам с путём к прошлому отчёту (`review-N-r2.md`). **Не больше двух повторных раундов**: после второго оставшиеся Critical/Important оркестратор сверяет с кодом сам, пишет датированную строку в `notes.md` и выносит вопрос пользователю.
4. `reports/report-N.md`, отметка `- [x] N. … (wip: <sha>, ревью rM ОДОБРЕНО)` в `tasks.md`.

small: один проход ревьюера на весь тикет, сценарий из `spec.md` проверить самому.

## architectural

1. **До первой задачи, один раз:** `devflow:fact-checker` на `spec.md` + `design.md`, отчёт `reports/fact-check.md`. НЕ ПОДТВЕРЖДЕНО и ТОЛКОВАНИЕ закрываются по колонке «кто решает» (`start.md` п. 5): источник, образец, умолчание — исправить решение, сценарии и «Контракт API» самому и дописать `Исправлено по проверке (дата): …`; пользователь — вопрос с рекомендацией, ответ строкой `Решение пользователя (дата): «его слова»`. ТРЕБУЕТ ПРОВЕРКИ — пользователю. «Не меняю, фиксирую» — нарушение. Без отчёта и без строк по опровергнутым решениям implementer не зовётся — `design-critique-gate.py` `[хук]`.
2. **По каждой задаче `plan.md`:** `devflow:implementer` с брифом (`brief.md`) → оркестратор коммитит результат, ещё не вызывая ревьюера (`git status --short`, явные пути, `wip(<KEY>): задача N`), SHA дописывает к задаче в `plan.md` (`(wip: <sha>)`) → `devflow:quality-reviewer` с `режим: subtask`, SHA литералом и файлом `reports/review-N-r1.md` (коммиты и правки истории у implementer закрыты хуком). Critical/Important — через SendMessage тому же implementer, новый коммит, повторный раунд по открытым находкам (путь к прошлому отчёту, `review-N-r2.md`); не больше двух повторных раундов, дальше — как в small/bounded п. 3.
3. После задачи — `tests_targeted` и `reports/report-N.md`.

**Критик на утверждения оркестратора.** Перед правкой, которая опирается на твоё обобщение — «все вызывающие уже проверяют X», «это единственный порядок вызовов», «класс больше никто не использует», «старых данных в этом состоянии нет», — вызови `devflow:decision-critic` (`brief.md`: утверждение в форме операции с «потому что», автор — оркестратор, чем проверено). `BLOCK` — правка не делается, строка в `notes.md` и вопрос пользователю. Чтение значения и механическая правка критика не требуют.

**Стоп петли black-box.** Раунды black-box в `finish.md` подчиняются тому же лимиту и трём признакам остановки: два раунда подряд тот же набор BLOCKER без новых доказательств; блокер второй раз подряд сидит в коде предыдущего исправления; флаки (воспроизвёл / нет / снова). Любой из них — не чинить, остановиться, датированная строка в `notes.md` и вопрос пользователю: продолжать или редизайн исходного решения. В петле «исправление → новый блокер из исправления» решение тяжелеет с каждым раундом, и зацикливание решает только человек.

Implementer по умолчанию — сабагент. Пользователь просит без сабагентов — реализуешь сам, но `devflow:quality-reviewer` и `devflow:black-box-tester` остаются: в T-2121 полный конвейер ревью пропустил треть недостающих тестов, проверяющий контур недостаточен, а не избыточен. Ревью не сокращается из-за дословного кода в брифе: в T-2122 дефект уровня Important сидел именно в нём.

## Отчёт подзадачи — `reports/report-N.md`

```markdown
# <KEY>, подзадача N: <название>

## Сделано

## Затронутые файлы

- путь:строка — что изменено

## Как проверено локально

Команды и фактический результат.

## Ревью

r1 НА ДОРАБОТКУ → r2 ОДОБРЕНО, `reports/review-N-r2.md`.

## Открытые риски

Если ничего нет — «нет».
```

Находки и отклонения от `design.md`/постановки — сразу датированной строкой в `reports/notes.md`. Сценарий приёмки по ходу реализации не меняется молча: изменение — решение пользователя, записанное в `spec.md` в разделе «Изменения сценариев» с датой; `black-box-tester` в `finish` отмечает такие сценарии как изменённые.

Мутационную проверку теста (сломать строку прод-кода, увидеть падение) делать только поверх коммита: `git checkout -- <файл>` откатывает к индексу и уносит незакоммиченную работу.

Дальше — `finish.md`.

# new-ticket — новая задача

Триггеры: «новая задача <KEY>», «изучи <KEY>», «проверь постановку <KEY>».

0. Тикет эпика (каталог в `<epics_dir>/<эпик>/tickets/<KEY>/` или ключ найден в `tasks.md` эпика — `catalog.md`) — сначала «Тикет эпика: вход» из `epics.md`: README эпика, раздел ключа в `tasks.md` с блоками «Передано из …», хвост `reports/notes.md`. Файлы тикета — в `<epics_dir>/<эпик>/tickets/<KEY>/` (пути ниже даны для обычного тикета).

1. Получить тикет и вложения (скилл `tracker`, `references/commands.md` → «Чтение тикета для task-workflow»):

- MCP YouTrack: `mcp__youtrack__get_issue` (id = `<KEY>`) и `mcp__youtrack__get_issue_comments` — все страницы;
- вложения: `node "$DEVFLOW_ROOT/skills/tracker/youtrack.mjs" attachments --key <KEY> --out <tasks_dir>/<KEY>/attachments`.

Сторона и общая задача (модель — `tracker/references/commands.md` → «Модель задач»; `side` и `side_field` — из `workflow.md`):

- дали **подзадачу своей стороны** — прочитать и её общую задачу (связь «subtask of»): смысл фичи и критерии приёмки фичи берутся оттуда, описание стороны — из подзадачи;
- дали **общую задачу** (сторона пустая) — `search_issues`: `subtask of: <KEY>`; подзадача стороны `side` одна — сказать пользователю «работаем по <ключ подзадачи>» и дальше вести её (каталог, ветка, `spec.md` — по её ключу); подзадачи своей стороны нет или их несколько — остановиться и спросить, свою подзадачу не создавать;
- дали **подзадачу другой стороны** — сказать, что репозиторий другой стороны, и спросить, продолжать ли.

MCP не подключён (инструментов `mcp__youtrack__*` нет в `ToolSearch`) — скажи пользователю и остановись, постановку по памяти не пересказывай. Вложения открыть (картинки и тексты — Read). Файл, который трекер не отдал (`error` в выводе), назвать пользователю. Если тикет ссылается на другой тикет («ранее оценивали в …») — прочитать и его, включая его каталог в `<tasks_dir>`.

2. Написать `<tasks_dir>/<KEY>/spec.md`:

```markdown
# <KEY>: <summary>

Ссылка: <url из конфига>
Общая задача: <ключ и summary общей задачи или «нет»>
Статус: <значение поля `status_field` из YouTrack>
Сторона: <back|front — поле стороны тикета>

## Кратко

2-4 предложения о сути задачи.

## Что нужно сделать

Пересказ критериев приёмки из description (без домысливания — если в тикете нет явных критериев, так и написать).

## Сценарии приёмки

Проверяемые сценарии: что именно будет считаться готовым. Вход для black-box-tester.

## Проверка постановки

Пробелы/неоднозначности списком, или «пробелов нет».

## Изменения сценариев

(появляется по ходу: дата — какой сценарий изменён и почему — решение пользователя)

## Передано из соседних тикетов эпика

Только для тикета эпика: каждый пункт блоков «Передано из …» раздела ключа в `tasks.md` эпика — с судьбой (в сценарий N / вне тикета — куда, решение пользователя / уже сделано — где). Блоков нет — «передач нет».

## Затрагиваемые модули (предварительно)

Беглая оценка по grep, не полное исследование.

## PR

(появится на шаге fixes)
```

3. Нет явных критериев приёмки (тикет описывает намерение, а не проверяемый результат) — не оставлять пусто: сформулировать сценарии самому и вынести на подтверждение вместе с вопросами. Сценарии приёмки фиксируются и подтверждаются пользователем **до реализации**: black-box и маршрут ревью строятся на них, сценарий, дописанный после кода, проверяет построенное. Расчётное требование — с числовым примером (вход → ожидаемое число).

   Задача очевидно small (одно место в коде, без публичного API, платежей, интеграции, нового эндпоинта) и критик постановки не нужен — записать в `spec.md` после `Статус:` строку `Размер: small (предварительно)`; `start.md` её уточнит. Без строки Stop-хук циклов потребует `spec-critic`.

   **Критика постановки.** Задача не очевидно small (больше одного места в коде, публичное API, платежи, интеграция, новый эндпоинт) — после записи `spec.md` запустить `devflow:spec-critic` с брифом: путь к `spec.md`, файл отчёта `reports/spec-critique.md`, пути карт модулей области из `<architecture_dir>` (по предполагаемым модулям; нет — «карт модулей нет»). Дописанные сценарии из отчёта перенести в «Сценарии приёмки» с пометкой «предложено», вопросы критика объединить со своими (дубли убрать). Критик видит постановку свежим взглядом: оркестратор, который уже «понял задачу», слеп к своим допущениям, а black-box-tester ловит дыры, когда код уже написан.

   **Критика расширения.** Любое расширение объёма относительно текста тикета — своё («заодно сделаем X») или пользователя («и ещё добавь Y») — до записи в `spec.md` проходит `devflow:decision-critic` (бриф по `brief.md`: утверждение «делаем X, потому что Y», автор, что проверено; отчёт `reports/critic-N.md`). Вердикт — пользователю до того, как расширение закрепилось в файле; `BLOCK` с «никакое требование не нарушим» — расширение отбрасывается или записывается как осознанное с датой. На чтение значения, механическую правку и вопрос пользователя критик не вызывается.

4. Перед вопросами — перечитать тикет и комментарии: написанное явно не спрашивать; зачёркнутое (`~~…~~`) — закрыто. Часть ли тикет эпика — спросить, только если это не следует из сообщения или постановки.

5. Краткое summary + вопросы (+ предложенные сценарии) — в чат. Если просили план или дизайн — его тоже в чат целиком, не ссылкой на файлы: выход режима — ревью пользователя; шаг «отправить клиенту / в тикет» не предлагать. Ветку **не создавать**. Ждать явного «добро». Уточнение, снятое в чате, записать в `spec.md` (раздел «Решения по постановке») и отдать текст для комментария в тикет пользователю (по `team-report.md`) — трекер из плагина не пишет.

## Частые проблемы

- **Нет отдельного поля под критерии** → пересказать из `description` своими словами, структуру не выдумывать.
- **Описание в Markdown YouTrack** → `get_issue` отдаёт как есть; пересказ делаешь ты.
- **Ошибка в постановке замечена уже во время реализации** → не додумывать и не менять scope молча: запись в `reports/notes.md`, вопрос пользователю.

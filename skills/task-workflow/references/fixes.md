# fixes — правки по существующему тикету

Триггеры: «вернись к <KEY>», «правки по ревью <KEY>», «тестер переоткрыл <KEY>», «в <KEY> упали тесты / CI», «в <KEY> баг» — в том числе первым сообщением о тикете в сессии. Ветка или PR могли появиться в другой сессии или у другого человека — факт их наличия важнее истории.

1. **Ветка.** `git fetch origin`; локальная `<KEY>` → `git checkout <KEY>` (+ `git pull --ff-only`, если в ветке чужие коммиты); только на remote → `git checkout -b <KEY> origin/<KEY>`; нигде нет → это новая задача: сказать пользователю и перейти к `new-ticket.md`.

   Ветку ребейзнул кто-то другой (ревьюер, конфликты) — сначала `pre-push-check.py` и тесты затронутых модулей, потом правки: сломанное до тебя иначе смешается с твоим диффом.

2. **Файлы тикета** — по `catalog.md`. Нет нигде — восстановить `spec.md` задним числом из `git log <KEY>` и тикета, пометить; уточнить, не часть ли эпика.

3. **Тип правок:**
   - **ревью PR** → скилл `resolve-pr-comments` (ссылка из сообщения или кэш `## PR` в `spec.md`; новая ссылка перебивает кэш и обновляет его);
   - **замечания тестировщика** → `mcp__youtrack__get_issue_comments` (id = `<KEY>`): комментарии после последнего перехода в «Reopened» (точное имя статуса — из схемы проекта), вложения — `youtrack.mjs attachments` (скилл `tracker`); зачёркнутое (`~~…~~`) не брать;
   - **упавшие тесты, CI, баг** → первый шаг диагностики — раздел «Проблема → трасса → код» карты модуля в `<architecture_dir>` (есть трасса под симптом — идти по её шагам); воспроизвести (вывод от пользователя, лог CI (`gh run view --log-failed`), иначе `tests_targeted`) **красным тестом на старом коде до фикса** — тест, зелёный до правки, диагноз не подтверждает; найти причину, **диагноз — критику до правки**: `devflow:decision-critic` с утверждением «причина бага — X, потому что Z», автором и тем, чем воспроизведено (`brief.md`, отчёт `reports/critic-N.md`); `BLOCK` или `REVISE` — вернуться к диагностике, не чинить по опровергнутому диагнозу. Потом починить.

4. **Шире точки замечания.** Однотипные места — по всему диффу ветки (`git diff origin/<base>...HEAD`), в этом же заходе. Новое исключение, значение или эффект метода — вызывающие по всей цепочке до входных точек.

5. **Проверки.** `tests_targeted`; если правка задевает общие модули — `tests_full`; последним — `pre-push-check.py`.

6. **`reports/fix-N.md`** (N — номер захода), первая строка — `# <KEY>, заход N: <ревью | тестер | баг | CI> — <дата>` (тип захода читает Stop-хук циклов: для `баг` и `CI` обязателен критик на диагноз); дальше что было, что поменялось, чем проверено.

7. **Коммит поверх, историю не переписывать.** Без `reset --soft`, `amend` и force — на коммит смотрит ревьюер, треды привязаны к строкам. Название предложить и дождаться подтверждения: по сути правки (`fix(<KEY>): сохранять номер транзакции при неуспешной оплате`); «правки после ревью» — только если правки действительно по ревью. За заход спросить один раз, как делить коммиты и отвечать ли в треды. Несколько независимых правок — несколько коммитов; после разбивки сверить дерево (`git diff --quiet <проверенный> HEAD`).

```bash
git status --short
git add <явные пути>
git commit -m "<согласованное название>"
```

Заход `ревью`: после коммита — `devflow:quality-reviewer` режим `subtask` по SHA захода, отчёт `reports/review-fix-N-r1.md` (шаг 5 `resolve-pr-comments`; Stop-хук требует его по `fix-N.md` типа `ревью`); находки — новым коммитом, `pre-push-check.py` после них заново.

Пуш — по команде, `branch-ops` D, обычный push без force. Отклонён — в ветку кто-то запушил: `git fetch`, `git log origin/<KEY>`, спросить; force не пробивать.

8. **Отчёт** — та же статус-строка, что в `finish.md`, плюс что сделано по каждому замечанию.

   Цикл режима (обязательные агенты, Stop-хук) — `cycles.md`.

9. Уроки — шаг 7 `resolve-pr-comments` (замечания ревьюера) или `/devflow:retro` (тестировщик, CI): дефекты назвал живой человек, это главный материал обучения.

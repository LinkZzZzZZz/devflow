# estimate — оценка

Триггеры: «<KEY> на оценку», «дай оценку в часах», «помоги оценить», «подгони под N ч».

Выход — декомпозиция и часы, не ветка и не код. Ветку не создавать.

1. Тикет — скиллом `tracker` (MCP YouTrack `get_issue` и `get_issue_comments`, вложения — `youtrack.mjs attachments`), `spec.md` как в `new-ticket.md`.
2. Ресёрч по коду: что реально придётся трогать — `devflow:system-mapper` с `режим: area` (`brief.md`): карта области `<KEY>/map.md` с impact по компонентам; оценка строится от impact по компонентам карты, не от ощущения.
3. `<tasks_dir>/<KEY>/estimate.md` — декомпозиция по пунктам с часами на каждый; до записи — `devflow:decision-critic` на декомпозицию («оцениваем N пунктами по M часов, потому что …», `reports/critic-N.md`): `BLOCK`/`REVISE` — пункт переоценивается или дробится. Цикл режима — `cycles.md`.
4. В чат — **текстом, не таблицей**, по формату секции «Оценка» конфига. По умолчанию:

```
1. <пункт> — 2-3 ч
2. <пункт> — 1 ч
Итого: N-M ч
```

   Декомпозицию и ключевые решения дизайна — в чат целиком, не ссылкой на файл: выход режима — ревью пользователя. Следующий шаг «отправить клиенту / в тикет» не предлагать — наружу отдаёт только пользователь (T-2217: план лёг в файлы, в чат ушли три строки и вопрос про отправку клиенту).
5. Оценка — для трекера; делать всё равно всё, что требует постановка. Просят уложиться в норматив — не подрезать молча: показать, какие пункты урезаны или вынесены, и риск этого.
6. Оценка для команды или в тикет (для тимлида, «подготовь коммент») — по `team-report.md`: этапы с итогом в заголовке, блоки по смыслу, числа из одного источника.
7. Открытые вопросы, влияющие на оценку, назвать и сначала попытаться закрыть самому (код, SQL-запрос, который пользователь выполнит), потом спрашивать.

# cycles — обязательные агенты по режимам

Единый источник: какой режим какие агенты и артефакты требует. Строки `[хук]` проверяет Stop-хук `cycle-check.py` по транскрипту сессии: нашёл признак режима, не нашёл вызова агента — блокирует завершение хода один раз с текстом, что вызвать. Строки `[слово]` — условные требования, их держит текст шага и считает `retro`.

| Режим | Признак (артефакт, записанный в сессии) | Обязательно |
|---|---|---|
| new-ticket | создан `<KEY>/spec.md` | `spec-critic` (не small) `[хук]`; `decision-critic` на расширения объёма `[слово]` |
| start / implement | создан `<KEY>/tasks.md` или `plan.md`; создан `<KEY>/design.md` | `system-mapper` area до tasks/plan `[хук]`; `decision-critic` на решения `design.md` `[хук]`; `spec-critic` с `режим: design` на `design.md` (обязательные блоки, «Паттерны и образцы в проекте») `[хук]`, его отчёт `reports/design-critique.md` — до `plan.md` и первого implementer, `fact-checker` с `reports/fact-check.md` и ответ пользователя по каждому опровергнутому решению — до первого implementer (PreToolUse `design-critique-gate.py`) `[хук]`; `decision-critic` на обобщения оркестратора в implement `[слово]` |
| finish | запуск `pre-push-check.py` оркестратором при записях в каталог тикета (без `fix-N.md`, ответов в треды и сквоша в сессии) | `system-mapper` feature `[хук]`; `quality-reviewer` branch `[хук]`; `black-box-tester` (bounded, architectural) `[хук]` |
| fixes (баг, CI) | `reports/fix-N.md` с типом захода `баг` или `CI` в заголовке | `decision-critic` на диагноз до правки `[хук]`; воспроизведение до фикса `[слово]` |
| estimate | `estimate.md` | `system-mapper` area `[хук]`; `decision-critic` на декомпозицию `[хук]` |
| research | `report.md` | `decision-critic` на выводы `[хук]`; `fact-checker` на утверждения о внешнем мире `[слово]` |
| review-pr | публикация ревью PR (`gh api …/pulls/<n>/reviews` на запись или `gh pr review`) | `system-mapper` feature по диффу PR `[хук]`; `quality-reviewer` pr `[хук]`; `decision-critic` на «не дефект» `[слово]` |
| resolve-pr-comments | ответ в тред (`gh api …/pulls/<n>/comments/<id>/replies`) с несогласием; `reports/fix-N.md` с типом захода `ревью` | `decision-critic` до ответа `[слово]`; `quality-reviewer` subtask по коммиту правок захода, до ответов в треды `[хук]` |

Размер читается из строки `Размер:` в `spec.md` рядом с признаком (`start.md` обязан её писать; new-ticket пишет `Размер: small (предварительно)`, когда критик постановки не нужен). Нет строки — размер неизвестен, условие «не small» считается выполненным, «bounded, architectural» — нет.

## Машинные строки

Формат: `- <режим>: <признак>[, <признак>] | <агент>[условие][, <агент>] | <что сделать>`. Признак — действие **оркестратора** (Write сабагента в транскрипт сессии не попадает): `write:<шаблон пути>[#<regex содержимого, без `|` и запятых>]` (`<KEY>` → ключ тикета, `N` → число; только Write — создание файла; Edit признаком не считается, правки `spec.md`/`tasks.md` идут в любом режиме), `mcp:<имя инструмента без префикса сервера>[!поле]` (`!поле` — вызов без этого поля в `input`), `gh:review` / `gh:reply` (Bash-команда `gh`, которая публикует ревью PR / отвечает в тред ревью; разбор — `hooks/lib_gh.py`, каталог тикета не нужен), `bash:<подстрока команды>` (учитывается только при Write в каталог `<KEY>/` за сессию — иначе ручной прогон проверок вне тикета блокировал бы ход). Признак с префиксом `!` обязан отсутствовать (отсекает соседний режим). Агент с суффиксом `#<regex>` (без `|`, запятых и `[`) засчитывается, только если regex найден в `prompt` вызова — так отличается режим брифа (`spec-critic#режим:\s*design` не закрывается вызовом в режиме spec из new-ticket той же сессии). Условие — `[не small]` или `[bounded, architectural]`, ставится после суффикса. Хук читает только этот раздел; маркер «уже блокировал» — на пару режим/агент и тикет.

- new-ticket: write:<KEY>/spec.md | spec-critic[не small] | запусти devflow:spec-critic на spec.md (бриф: путь spec.md, отчёт reports/spec-critique.md, пути карт модулей области или «карт модулей нет»); строка «Размер: small (предварительно)» допустима только на шаге new-ticket для очевидно small задачи, не для обхода
- start: write:<KEY>/tasks.md, write:<KEY>/plan.md | system-mapper | запусти devflow:system-mapper с «режим: area» (бриф по brief.md: spec.md, модули, architecture_dir) — выход <KEY>/map.md, покажи его пользователю
- start: write:<KEY>/design.md | decision-critic | решения design.md без критика: на каждое решение «Принятых решений» вызови devflow:decision-critic (бриф по brief.md: spec.md, утверждение «делаем X, потому что Y», автор, что проверено), отчёт reports/critic-N.md
- start: write:<KEY>/design.md | spec-critic#режим:\s*design | design.md без проверки: вызови devflow:spec-critic, первая строка брифа «режим: design» (бриф: spec.md, design.md, <KEY>/map.md, пути карт модулей, отчёт reports/design-critique.md) — он проверяет обязательные блоки, в том числе «Паттерны и образцы в проекте» (паттерн и образец с путём и слоем по каждому новому компоненту)
- finish: bash:pre-push-check.py, !write:<KEY>/reports/fix-N.md, !gh:review, !gh:reply, !bash:reset --soft | system-mapper, quality-reviewer, black-box-tester[bounded, architectural] | finish.md: system-mapper «режим: feature» → reports/feature-map.md; quality-reviewer «режим: branch» → reports/branch-review.md; black-box-tester «режим: coverage» и «execute» → reports/test-report.md
- fixes: write:<KEY>/reports/fix-N.md#заход \d+: баг, write:<KEY>/reports/fix-N.md#заход \d+: CI | decision-critic | перед правкой по диагнозу вызови devflow:decision-critic (бриф по brief.md: тикет, утверждение «причина бага — X, потому что Z», автор, что проверено), отчёт reports/critic-N.md
- estimate: write:<KEY>/estimate.md | system-mapper, decision-critic | estimate.md: system-mapper «режим: area» для impact по компонентам, затем decision-critic на декомпозицию («оцениваем X пунктами, потому что …»), отчёт reports/critic-N.md
- research: write:<KEY>/report.md | decision-critic | до отправки report.md вызови devflow:decision-critic на каждый вывод («X возможно, потому что …»), отчёт reports/critic-N.md
- review-pr: gh:review | system-mapper, quality-reviewer | review-pr шаг 2: system-mapper «режим: feature» по диффу PR (маршрут по требованиям) и quality-reviewer «режим: pr» — до публикации ревью
- resolve-pr-comments: write:<KEY>/reports/fix-N.md#заход \d+: ревью | quality-reviewer#режим:\s*subtask | resolve-pr-comments шаг 5: после коммита правок захода вызови devflow:quality-reviewer, первая строка брифа «режим: subtask» (бриф по brief.md: SHA коммита литералом, отчёт reports/review-fix-N-r1.md); Critical/Important — починить новым коммитом и повторный раунд по открытым находкам; pre-push-check.py — после ревью, последним

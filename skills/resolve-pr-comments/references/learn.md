# learn — уроки из замечаний ревью

Замечание живого ревьюера — главный материал обучения плагина: либо правила нет, либо оно есть и не сработало. Этот справочник описывает журнал находок, ключи кластеров, бриф классификации, порядок сверки и формат кандидатов. Используют: шаг 7 `resolve-pr-comments`, команда `/devflow:learn-pr`, шаг 3 `/devflow:retro`.

## 1. Журнал находок

Файл — `review-findings.jsonl` рядом с `.env` плагина (`python3 "$DEVFLOW_ROOT/hooks/lib_env.py" env-path` → каталог). Личный, в репозиториях проектов не лежит. Одна строка — одна находка живого ревьюера:

| поле | значение |
|---|---|
| `project` | `github_repo` конфига или `<owner>/<repo>` из URL PR |
| `pr` | `<project>#<номер>` |
| `thread` | `id` треда из `reviewThreads` (GraphQL); `""`, если неизвестен |
| `date` | дата первой заметки треда |
| `reviewer` | username ревьюера |
| `severity` | `critical` / `important` / `low` / `unknown` — как пометил ревьюер |
| `loc` | `файл:строка` или `""` |
| `defect` | суть дефекта, до 20 слов |
| `category` | `race`, `test-weak`, `test-missing`, `layering`, `n+1-query`, `dead-code-copy`, `callers-chain`, `api-contract`, `implicit-contract`, `error-handling`, `naming-style`, `spec-mismatch`, `migration-schema`, `security`, `external-api`, `other` |
| `checklist` | номер пункта чек-листа `quality-reviewer`, который должен был поймать; `P` — проектное правило; `none` |
| `rule` | правило императивом, обобщённо, без имён классов проекта |
| `how_found` | `static` / `ran-tests` / `mutation` / `linter` / `stack` / `unknown` |
| `author_reaction` | `accepted` / `disputed` / `partial` / `none` |
| `project_specific` | `true`, если правило имеет смысл только в этом проекте |
| `rule_key` | ключ кластера из §2 |
| `decision` | `rule:<путь>:<строка>` · `checklist:<N>` · `project:<файл>` · `mechanic:<хук или pre_push>` · `memory:<файл>` · `rejected:<почему>` · `pending`. До разбора — `pending` |
| `decided_at` | дата решения |

Дедупликация: при разборе тред пропускается, если его `(project, pr, thread)` уже в журнале; строка журнала опознаётся и по `(project, pr, thread, defect)`, и по `(project, pr, loc, defect)`. Запись строки — после «ок» пользователя по кандидату (или `rejected`), через Bash heredoc `>>`.

Подтверждённое замечание — тред `isResolved: true`, с ответом автора или без: резолв без ответа значит «исправлено». `disputed` — отдельный список, в правила не идёт без решения пользователя.

## 3. Бриф классификации тредов (для сабагента при пачке PR)

Сабагент `general-purpose` получает файл с дампом тредов (заголовок PR, затем треды: id, isResolved, path:line, заметки с автором и датой) и пишет JSONL по схеме §1 без `rule_key`/`decision` (их проставляет сид или оркестратор). Текст брифа:

> Ты читаешь дамп тредов ревью к PR одного автора. Один тред может содержать несколько пронумерованных находок — каждую считай отдельно. Сначала прочитай CHECKLIST (`agents/quality-reviewer.md`, «Общий чек-лист») и RULES (`rules/general.md`, §5). Прочитай дамп целиком частями, не пропуская треды. По каждой находке — одна JSON-строка с полями: pr, date, reviewer, severity (как пометил ревьюер; не помечено — `unknown`), loc, defect (до 20 слов), category, checklist (номер пункта, `P` или `none`), rule (императив, обобщённо; если дословно есть в CHECKLIST — `=п.N`), how_found (по словам ревьюера), author_reaction, project_specific. Не выдумывай: нет в тексте — `unknown`/`""`. В конце выведи число записанных строк, число тредов (`grep -c '^## thread'`) и число пропущенных не-находок (вопрос, обсуждение, одобрение) — счёт должен сходиться. Ответ оркестратору — только путь к JSONL и три числа.

## 4. Порядок сверки кандидата

По каждой подтверждённой находке, в таком порядке:

1. **Журнал** — `grep -c '"rule_key": "<ключ>"'`: тот же ключ уже есть → повтор (k-й); у прошлой строки `decision: checklist:*|rule:*` → «правило есть, не сработало».
2. **Чек-лист `quality-reviewer`** — пункт есть → почему не сработал: формулировка (пункт не называет этот случай), режим (поймалось бы только в `branch`/`subtask`), калибровка (нашли, но поставили Minor), нужен запуск (мутация, линтер, стенд). Ответ определяет предложение: уточнить пункт / сменить режим / калибровка / механика.
3. **`rules/general.md`** — для правил поведения и процесса.
4. **`CLAUDE.md` проекта и карта «Ревью» `workflow.md`** — для проектных конвенций (`project_specific`).
5. **Память проекта** — `description:` файлов `~/.claude/projects/<путь>/memory/`.

Куда ложится кандидат:

- общий дефект без пункта → чек-лист `quality-reviewer` (новый пункт только при кластере ≥10 находок, иначе — дополнение существующего пункта); правило поведения → `rules/general.md` (лимит 80 строк);
- пункт есть, не сработал → уточнение формулировки пункта, режима или калибровки; «нужен запуск» → механика: `pre_push` проекта, хук, шаг ревью;
- проектная конвенция → `CLAUDE.md` проекта с меткой `[ревьюер]` или файл из карты «Ревью»; из worktree — текст пользователю. До предложения — сверка с кодом: грепом счёт мест, которые следуют правилу и нарушают его, соседние правила свода, существование названных enum, файлов и хелперов; большинство кода не следует — сузить правило или оговорить техдолг, исключения назвать в самом правиле;
- первое появление сомнительного урока → память проекта;
- `disputed` → в журнал с `rejected:<аргумент>`, в правила не идёт.

Запись в плагин — по шагам 4–5 `/devflow:rule`; пачка кандидатов — один релиз: `minor`, если добавлен пункт чек-листа или команда, иначе `patch`; строка CHANGELOG перечисляет `rule_key`.

## 5. Формат списка кандидатов

```
Кандидаты (N), повторов M, спорных L:
1. [rule_key] <замечание одной строкой> (<pr>, <ревьюер>, <уровень>)
   Есть: <пункт N / правило / нет>. Почему не сработало: <формулировка | режим | калибровка | нужен запуск | —>
   Предложение: <императив, одна-две строки>
   Куда: <чек-лист п.N | rules/general.md §K | CLAUDE.md проекта | pre_push/хук | память>   Повтор: <k-й | нет>
…
Спорные (L): <pr> <loc> — <суть>, аргумент автора: <…>
```

Ноль кандидатов — нормальный исход: не выдумывай, чтобы отчитаться. После «ок» по каждому — запись и строка журнала; сводка: записано K, отклонено R, в журнал — все.

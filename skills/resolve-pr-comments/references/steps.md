# resolve-pr-comments — шаги 1–7

Маршрут: `SKILL.md` §2. Здесь — дословные шаги и команды `gh`.

## Команды GitHub

Чтение — свободно; запись (`gh api` на запись, `gh pr edit`) подтверждает хук `guard-bash-rules`.
- `gh pr view <n> --json number,title,body,url,headRefName,headRefOid,baseRefName` — общий статус PR
- треды со статусом — GraphQL `reviewThreads` (в REST у комментария статуса «resolved» нет):
  ```bash
  gh api graphql -F owner='{owner}' -F name='{repo}' -F number=<n> -f query='
    query($owner: String!, $name: String!, $number: Int!, $after: String) {
      repository(owner: $owner, name: $name) { pullRequest(number: $number) {
        reviewThreads(first: 100, after: $after) { pageInfo { hasNextPage endCursor }
          nodes { id isResolved isOutdated path line
            comments(first: 50) { nodes { fullDatabaseId author { login } body createdAt } } } } } } }'
  ```
  `hasNextPage: true` — повторить с `-F after=<endCursor>`
- общие комментарии PR (не к строкам) — `gh pr view <n> --json comments`
- ответ в тред — `gh api repos/{owner}/{repo}/pulls/<n>/comments/<fullDatabaseId первого комментария треда>/replies -f body='…'` (ответ на ответ API не принимает)
- правка описания PR — `gh pr edit <n> --body-file <файл>`
- резолв треда — только если пользователь явно попросил: `gh api graphql -f query='mutation { resolveReviewThread(input: {threadId: "<id треда>"}) { thread { isResolved } } }'`; по умолчанию резолв оставляем ревьюеру


## Шаги

### 1. Получить обсуждения

```
gh pr view <n> --json number,title,url,headRefName,headRefOid,baseRefName
reviewThreads (GraphQL выше) — все страницы; общие комментарии — gh pr view <n> --json comments
```

### 2. Посчитать и разобрать

| Статус | Признак |
|--------|---------|
| Уже исправлено | тред `isResolved: true` |
| Открыто | тред `isResolved: false` |
| Не в счёт | общие комментарии ботов и CI, без вопроса к коду |

Общий комментарий PR от человека с замечанием — тоже пункт разбора (статуса у него нет: открыт, пока автор не ответил по сути). Первой строкой пользователю — точный счёт: `Открытых тредов: N (из M)`. «Всё решено» без счёта не писать; сколько было открыто — столько должно быть закрыто в итоге или названо, почему нет.

Открытый тред, где последний комментарий ревьюера новее последнего ответа автора, — пункт этого раунда: разобрать и ответить, даже если автор уже отвечал или в журнале тред записан как `rejected` / `disputed`.

### 3. Критически разобрать каждый открытый

**Ревьюер может ошибаться.** Прочитай файл и строки, контекст, оцени сам:
- проблема реально есть в коде?
- предложенное решение верно и не создаёт новых проблем?
- нет ли у ревьюера неполной информации?

| Исход | Действие |
|-------|---------|
| Верен, решение очевидно | предложить правку одной строкой |
| Верен, решение неоднозначно | 2-3 варианта с trade-off, вопрос пользователю |
| Спорный или ошибочный | почему, с кодом и аргументами — пользователь решает |

Исход «спорный или ошибочный» до ответа «не согласен» проходит `devflow:decision-critic` (бриф по `task-workflow/references/brief.md`: утверждение «замечание неверно, потому что …», автор — оркестратор, чем проверено; отчёт `reports/critic-N.md` в каталоге тикета, без тикета — в scratchpad сессии). `BLOCK` — замечание верно, тред идёт в правку; несущую находку сверь по коду сам. Цикл режима — `task-workflow/references/cycles.md`.

Второй раунд подряд контрпример к одной эвристике (факт выводится из косвенных признаков) — не латать её: найти место, где факт известен точно, и записывать его там; варианты — пользователю.

Разбор всех тредов — пользователю одним списком. **Правки — после его «да».** В auto-режиме треды с очевидным решением можно чинить без вопроса; спорные и неоднозначные — всегда на вопрос.

Уточнение постановки или продукта — спросить пользователя в чате, не в треде.

### 4. Починить подтверждённое

Правила кода — проектный `CLAUDE.md` (метки `[ревьюер]`/`[слово]`) и файлы из карты «Ревью» `workflow.md`. Комментарий им противоречит — дополнительный аргумент считать его спорным.

Тред с контрпримером ревьюера (числа, сценарий пробы): сначала его входы — тестом с его числами, красным на текущем коде; потом правка; ответ — когда эти тесты зелёные.

Последовательно; после каждой правки — `tests_targeted` по затронутому, не копить.

**Шире треда.** Каждое подтверждённое замечание проверить по всему диффу ветки (`git diff origin/<base>...HEAD`): то же нарушение в других файлах — чинить в этом же заходе и сказать об этом в ответе. Новое исключение или значение — вызывающие по всей цепочке.

Правка добавила методу новый исход (`false`, `null`, исключение, «не записано») — в брифе ревьюера (шаг 5) назови метод и исход: п. 12, вызывающие по всей цепочке.

Замечание о границах модулей закрыто только нулевым приростом нарушений по файлам ветки против базы; «новые вхождения давних пар» — не закрытие.

### 5. Ревью правок и проверки

1. Коммит захода — по правилам `task-workflow` (`fixes.md` шаги 6–7): `reports/fix-N.md` с типом `ревью`, коммит поверх, название согласовать.
2. `devflow:quality-reviewer`, первая строка брифа `режим: subtask` (бриф по `task-workflow/references/brief.md`): SHA коммита захода литералом (несколько коммитов — диапазон), отчёт `reports/review-fix-N-r1.md` (N — номер захода; без тикета — в scratchpad сессии), новые исходы методов из шага 4. Правила кода ревьюеру не передаются — у него свой чек-лист и `[ревьюер]` проектного `CLAUDE.md`. Critical/Important — починить, новый коммит, повторный раунд по открытым находкам с путём прошлого отчёта (`review-fix-N-r2.md`); не больше двух повторных раундов, дальше — сверить с кодом самому и вынести пользователю. Без ревью Stop-хук циклов не отпускает ход.
3. `tests_targeted` по ходу; `tests_full` — если правки задевают общие модули (один раз, последовательно).
4. Последним — `$DEVFLOW_ROOT/hooks/pre-push-check.py` на финальном дереве (любая правка после, в том числе по находке ревьюера, обнуляет).

Падения сверить: наши или pre-existing (сравнить с `origin/<base>`). **В отчёте называй прогнанные проверки** — «чисто» без перечня запрещено.


### 6. Ответы в треды

Тексты ответов по каждому треду — пользователю одним списком, дословно и целиком, без сокращений и «…», у каждого утверждения о поведении — чем подтверждено (тест, мутация, замер). Черновиков, видимых только автору, у ответов в треды GitHub нет: список в чате и есть черновик. После «ок» (и его правок формулировок) — по ответу на тред: `gh api repos/{owner}/{repo}/pulls/<n>/comments/<fullDatabaseId>/replies -f body='<текст>'`; хук покажет каждый запрос. Ответ на общий комментарий PR — `gh pr comment <n> --body-file <файл>`.

Стиль — секция «Ответы в PR» конфига; калибровка — реплики пользователя в этом же PR. Общее:
- 1-3 коротких предложения, без вступлений, благодарностей и извинений;
- без markdown;
- сразу суть: что поменяли / почему не актуально / что уточнили;
- каждое утверждение о поведении в ответе и в правке описания PR («не менялось», «не растёт», «ради производительности», «закреплено тестом») до черновика сверь с кодом, тестом или замером ветки; не подтверждается — переформулируй или убери; ревьюер принёс входы — «есть кейсами» и «закрыто» только про тесты с его числами, красные до правки, свой похожий сценарий не в счёт; обобщение («любой», «все», «закрыты», «совпадает», «правило X держится») — только если его держит мутация, иначе перечисли проверенные случаи; довод частотой или таймингом («редко», «через 5 минут, значит реже») — только с замером;
- очевидное — совсем коротко («убрал», «поправил»).

### 7. Уроки

Справочник — `$DEVFLOW_ROOT/skills/resolve-pr-comments/references/learn.md` (журнал, ключи `rule_key`, порядок сверки, формат кандидатов). Делается после коммита правок, до отчёта.

1. По каждому подтверждённому треду (исправлен сейчас или ранее; `resolved` без ответа автора — тоже), чей `(project, pr, thread)` ещё не в журнале (уже есть — пропустить и посчитать): категория, `rule_key`, уровень, как ревьюер нашёл (по его словам), реакция. Спорные (`disputed`) — отдельным списком.
2. Сверка в порядке `learn.md` §4: журнал (повтор?) → чек-лист `quality-reviewer` (пункт есть → почему не сработал: формулировка, режим, калибровка, нужен запуск) → `rules/general.md` → `CLAUDE.md` проекта и карта «Ревью» → память проекта.
3. Кандидаты — пользователю одним списком в формате `learn.md` §5: замечание, что уже есть, предложение императивом, адрес записи, повтор ли. Ноль кандидатов — нормальный исход, не выдумывать.
4. После «ок» по каждому — запись: в плагин по шагам 4–5 `/devflow:rule` (пачка — один релиз, `minor` при новом пункте или команде, строка CHANGELOG перечисляет `rule_key`); в проект — правка `CLAUDE.md` или файла из карты, из worktree — текст пользователю; в память — файл по формату `/devflow:retro`. В журнал — строка по каждой находке всегда: принятое с `decision` по адресу, отклонённое — `rejected:<почему>`, спорное — `rejected:<аргумент автора>`. В auto-режиме гейт «ок» сохраняется: это запись в правила, не правка кода.

## Формат итога

```
Открытых тредов было: N

Уже исправлено ранее (K):
- file:line — кратко

Исправлено сейчас (M):
- file:line — что изменено и почему верно (+ те же места: file:line, …)

Спорные / требуют решения (L):
- file:line — суть
  Анализ: …
  Варианты: A) … | B) … | C) оставить (аргументы)

Тесты: <команда> — N passed, M failed (pre-existing: …)
Ревью правок: review-fix-N-r1.md — K находок (Critical/Important M), закрыто коммитом <sha> | без находок
Проверки: pre_push на <sha> — <результат>
Ответы на GitHub: N тредов, отправлены | ждут «ок»
Уроки: кандидатов N (повторов M, спорных L) | записано K, отклонено R | ждут «ок»
```

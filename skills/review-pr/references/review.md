# review-pr — контекст, ревью, публикация

## 1. Контекст

- Из ссылки — `<owner>/<repo>` и номер PR. `gh pr view <n> --repo <owner>/<repo> --json number,title,body,author,baseRefName,headRefName,headRefOid,files,url` (нужны `baseRefName`, `headRefName`, `headRefOid` — head-коммит, на него ставятся комментарии), дифф — `gh pr diff <n>`.
- Номер тикета в заголовке, ветке или описании (`<KEY>`, формат — поле `key` в `.claude/workflow.md`) — прочитай тикет (скилл `tracker`: MCP YouTrack `get_issue`, `get_issue_comments`, вложения — `youtrack.mjs attachments`) до чтения кода: ревью проверяет и соответствие постановке, и отсутствие лишнего.
- Для чтения кода целиком: `git fetch origin <headRefName>` и `git show origin/<headRefName>:<файл>`; рабочий каталог пользователя не переключай. PR из форка — `git fetch origin pull/<n>/head:pr-<n>` и `git show pr-<n>:<файл>`.


## 2. Ревью

Проектный слой ревью — правила с меткой `[ревьюер]` в `CLAUDE.md` основного репозитория плюс файлы из карты «Ревью» `.claude/workflow.md`. Пройди его вместе с общими пунктами; найденное по нему помечай номером P-пункта.

- Маршрут по требованиям: `devflow:system-mapper` с `режим: feature` (бриф по `task-workflow/references/brief.md`: критерии тикета как `spec.md` или путь к нему, диапазон `origin/<base>...origin/<head>` литералом; выход `reports/feature-map.md` в каталоге тикета, без тикета — в scratchpad) — по каждому требованию цепочка `Class::method()`; разделы «Не реализовано или не найдено» и «Вне сценариев» — кандидаты в находки. Ревью идёт по маршруту, не по диффу подряд.
- Запусти агента `devflow:quality-reviewer` с `режим: pr` (из плагина; проектный `.claude/agents/*reviewer*.md` приоритетнее) на диффе PR с командой `git diff origin/<base>...origin/<head>` — он проходит чек-лист проекта. Оба агента — до публикации: Stop-хук циклов (`task-workflow/references/cycles.md`) блокирует ход с публикацией ревью без них. Он может быть описан для одной подзадачи; дифф всего PR ему подходит, чек-лист тот же. Сам параллельно проверь корректность против тикета: граничные случаи, ошибки, транзакции, гонки, N+1, контракт публичного API.
- Оценивай только строки, которые PR добавляет или меняет. Проблему в соседнем старом коде помечай «вне PR».
- Каждую находку подтверди по коду: путь и строка в новой версии файла. Предположение без проверки — не находка, а вопрос автору, и так и помечается.
- Утверждения автора в описании PR («не менялось», «закрыто тестом», «все вызывающие проверены») и своё «это не дефект» по месту, которое выглядело подозрительно, — `devflow:decision-critic` (бриф по `task-workflow/references/brief.md`: утверждение с «потому что», автор — автор PR или оркестратор, чем проверено; отчёт `reports/critic-N.md` в каталоге тикета, без тикета — в scratchpad). `BLOCK` — находка в список ответа (`SKILL.md` §4) со ссылкой на контрпример.


## 4. Публикация выбранного

Ревью на GitHub публикуется одним запросом — `POST /repos/{owner}/{repo}/pulls/{n}/reviews` с массивом комментариев (https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request). Черновиков, видимых только тебе, здесь нет: файл ревью и есть черновик, его сверяешь до отправки.

1. Правки из ответа пользователя: готовый текст — вставь дословно; условие («мягче», «без имени») — перепиши коммент под него, сохранив суть. Ответ «публикуй N, M» — это и выбор, и согласие на публикацию: в чате не переспрашивай, подтверждение даст хук на шаге 3.
2. Собери файл ревью (`reports/pr-review-<n>.json` в каталоге тикета, без тикета — scratchpad):
   ```json
   {
     "commit_id": "<headRefOid>",
     "event": "COMMENT",
     "body": "",
     "comments": [
       {"path": "app/Services/LessonService.php", "line": 42, "side": "RIGHT", "body": "<текст треда>"}
     ]
   }
   ```
   По комментарию на выбранный пункт; `line` — строка новой версии файла, `side: RIGHT` — новая сторона диффа. Диапазон строк — добавь `start_line` и `start_side`. GitHub отклонил запрос (422, «Validation failed») — проверь, что строка есть в диффе PR; нет — комментарий без позиции переносится в `body` ревью с `path:line` в тексте. `event` — `COMMENT`, если пользователь не сказал «одобряю» (`APPROVE`) или «запроси правки» (`REQUEST_CHANGES`; для него `body` обязателен).
3. Сверь файл: комментариев ровно столько, сколько выбрано, тексты те. Отправь одним вызовом: `gh api repos/{owner}/{repo}/pulls/<n>/reviews --input <файл>`. Хук покажет число комментариев, файлы и событие и спросит подтверждение.
4. Ответ API — ссылка на ревью (`html_url`); пользователю — «опубликовано ревью: N комментариев» и ссылка.

# branch-ops — операция E

Общий протокол (fetch, старые SHA, worktree, конфликты, сверка, проверки, стоп перед пушем) — в `references/protocol.md`, он действует и здесь.

## E. Синхронизация своих PR

«В PR конфликты», «снова конфликты в T-21», «проверь мои PR», «/sync-prs». Назван конкретный PR или ветка — сразу шаг 4 для неё.

1. `gh pr list --author "@me" --state open --json number,title,headRefName,baseRefName,isDraft,mergeable,mergeStateStatus,body,url`; черновики (`isDraft: true`) пропусти, если их не назвали.
2. `git fetch origin --prune`. По каждому PR: `mergeable` (`CONFLICTING` / `MERGEABLE` / `UNKNOWN`), `mergeStateStatus` (`DIRTY` — конфликт, `BEHIND` — ветка отстала от базы) и отставание `git rev-list --count origin/<head>..origin/<base>`. `UNKNOWN` — GitHub ещё считает; повтори запрос позже, не угадывай.
3. Переносить: `mergeable: CONFLICTING` (или `mergeStateStatus: DIRTY`). `BEHIND` без конфликта переносить, только если база требует актуальной ветки для вливания или пользователь попросил: force-push перезапускает проверки CI и может сбросить одобрения.
3а. Исключение из шага 3: если в описании PR назван конфликт по смыслу с другим PR («вливающемуся вторым — добавить …») и тот PR уже влит в базу, перенеси ветку, даже когда текстового конфликта нет. В том же заходе внеси обещанное (фильтр, предикат, поле) отдельным коммитом с тестом — до того, как это найдёт ревью.
4. Каждую ветку — операцией A на `origin/<base>` из PR. Если `git merge-base` показывает, что ветка отведена не от базы PR (например, PR нацелен на `main`, а ветка стоит на `release`) — стоп и вопрос: ребейз на базу PR перетащит в него чужие коммиты. Если одна ветка отведена от другой из списка — сначала базовую, затем зависимую `--onto`.
5. Один сводный отчёт с блоком A на каждую ветку и одна команда на пуш всех.

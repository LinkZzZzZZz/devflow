# branch-ops — операция D

Общий протокол (fetch, старые SHA, worktree, конфликты, сверка, проверки, стоп перед пушем) — в `references/protocol.md`, он действует и здесь.

## D. Отправка ветки задачи

«Сделай коммит от текущей временной метки и пушь», «засквошь и запушь», «/ship T-123». Временный worktree не нужен: работай там, где ветка выписана (`git worktree list`), — незакоммиченная работа задачи лежит там.

1. `git fetch origin`. Граница опубликованного: `origin/<ветка>`, если она есть. Коммиты до неё видел ревьюер — их не переписывай. Нет ветки на origin — граница `git merge-base HEAD origin/<база>`.
2. Незакоммиченное: `git status --short`. Отслеживаемые изменения входят в коммит, **кроме файлов из «Не коммитить»** (`local_wip`) — их не добавляй и упомяни одной строкой; неотслеживаемые файлы перечисли в отчёте и не добавляй без слова пользователя.
3. Проверки — `$DEVFLOW_ROOT/hooks/pre-push-check.py` (legacy: `checks` из `branch-ops.md`) — на финальном рабочем дереве, после последней правки. Хук сверяет содержимое дерева, а не SHA, поэтому прогон до коммита засчитывается коммиту с тем же содержимым. Упали — чини и прогоняй снова.
   Ветку перед отправкой ребейзнули на базу, ушедшую вперёд после полного прогона, — `tests_full` повторить на новом HEAD до пуша, упавшее сверить с базой: совпадение патча не значит, что тесты пройдут на новых зависимостях базы.
4. Ветка на ревью, рабочее дерево чистое (кроме «Не коммитить»), а после границы уже лежат коммиты с согласованными названиями (их сделал `task-workflow` fixes) — шаги 4–5 пропусти: ничего не переписывай и не переименовывай, сразу к пушу (шаг 6) обычным `git push origin HEAD:<ветка>`.
   Иначе — состав и названия. Первая отправка (ветки нет на origin) — один коммит на всю задачу. Ветка на ревью — один коммит на каждую независимую правку; одна правка или пользователь сказал «одним коммитом» — один. Названия — из команды пользователя (`/ship T-N fix(T-N): …`); не даны — составь по формату из конфига (`Коммиты`, «Название коммита» ниже) и по сути диффа (`git diff --stat <граница>`) и предложи одним сообщением вместе с итогом проверок: «Коммиты: `<название 1>` (<файлы>), `<название 2>` (<файлы>); проверки ✓. Коммичу и пушу?». PR для ветки ещё нет (шаг 7) — в то же сообщение заголовок PR, ревьюер и описание целиком, вопрос «Коммичу, пушу и создаю PR?». Ответ «да» — согласие и на разбивку, и на названия, и на PR, и команда на пуш; поправки пользователя применяй и не переспрашивай. «Правки после ревью» — только если ревью действительно было.
5. Коммит: `git reset --soft <граница>`, затем `git commit -m "<название>"` — один раз или по коммиту на правку (`git add <файлы правки>` перед каждым); автор и дата получаются текущими, это и есть «от текущей временной метки». После `reset --soft` проверь индекс (`git diff --cached --name-only`): файлов из «Не коммитить» там быть не должно — уберёт `git restore --staged <файл>`. После коммита `git status --short` показывает только их. Совпадение дерева коммита с проверенным сверит хук при пуше.
6. Пуш: история переписана относительно `origin/<ветка>` — `git push --force-with-lease=<ветка>:<старый SHA> origin HEAD:<ветка>`, иначе `git push origin HEAD:<ветка>`.
7. PR: `gh pr list --head <ветка> --state open --json number,url`. Есть — не трогай, к шагу 8. Нет — создай после пуша:
   - заголовок — название коммита (при нескольких коммитах — суть задачи по тому же формату);
   - описание — по «Описание PR» ниже, в файл `<каталог тикета>/reports/pr-body.md`;
   - база (`--base`) — `base` из «Git» конфига (у ветки эпика — её эпик-ветка);
   - ревьюер (`--reviewer`) — логин GitHub того, кто ревьюит: из тикета YouTrack (поле ревьюера, если оно есть в проекте) или со слов пользователя; имя в YouTrack и логин GitHub не совпадают — спроси, не угадывай; пусто — без `--reviewer`;
   - не черновик.
   Заголовок и описание пользователь видит до создания: в сообщении шага 4 или, если шаги 4–5 пропущены, отдельным сообщением с вопросом «Создаю PR?» — после «да»:
   ```bash
   gh pr create --base <база> --head <ветка> --title "<заголовок>" --body-file <каталог тикета>/reports/pr-body.md [--reviewer <логин>]
   ```
   Хук `guard-bash-rules` покажет заголовок, ветки, ревьюера и начало описания ещё раз; `gh pr create --fill`, `--web`, `--editor` и вызов без `--title`/`--body-file` он отклоняет — заголовок и описание пользователь должен увидеть до создания.
8. Проверки CI: `gh pr checks <ветка>` — статус каждой проверки на новом SHA и ссылки. Упала (`fail`) — назови проверку и займись ею. Идут (`pending`, код выхода 8) — так и скажи.

## Название коммита

Формат — из «Git» конфига (`тип(<KEY>): суть`). Одна суть изменения, ориентир 60–80 символов вместе с префиксом. Перечисление деталей, случаев, исключений и списков («— сеть, таймауты, 5xx и 429 не запоминаются, ротация снимает метку») — в описание PR, не в название.

- плохо: `fix(T-12): отказ во входе запоминается на 30 с - сеть, таймауты, 5xx, 429 и 400 не запоминаются, текст отказа не хранится, ротация ключа снимает метку`
- хорошо: `fix(T-12): отказ во входе по ключу запоминается на 30 с`

## Описание PR

Источники: отчёт `finish` (что сделано, как проверено, что осталось непроверенным, вне зоны), `reports/` и `notes.md` тикета, `git diff --stat origin/<база>...HEAD`. Пиши голосом пользователя, по сути, без благодарностей.

- **Что сделано** — пункт на изменение: путь файла или класс/метод в бэктиках и что поменялось в поведении; несколько правок одного файла — вложенными пунктами. Что сознательно не менялось (вызывающие, соседний код) — отдельным пунктом.
- **Проверки** — только то, что реально прогонялось: команды и наборы с числами (typecheck, линтер, тесты: N наборов, M тестов), какие случаи покрывают новые тесты, мутации (N из M краснеют), ревью (какие роли, сколько кругов, итог).
- **Открытые вопросы и замечания** — нумерованный список: конфликты с открытыми PR в ту же базу (номер, файл, что править вливающемуся вторым; пересечение — `gh pr list --base <база> --state open --json number,headRefName,files` против `git diff --name-only`), сознательные компромиссы, что вне объёма и просит отдельной задачи, что не запускалось и почему. Пусто — раздел опусти.
- **Отклонения от постановки** — перед «Открытыми вопросами», нумерованный список из блока «отклонения от постановки» отчёта `finish`: что сужено, исключено или перенесено — причина, ссылка на решение. Ревьюер иначе находит это сам и просит зафиксировать до ревью. Пусто — раздел опусти.
- Утверждение о поведении, причине или цене решения пиши, только сверив его с кодом, тестом или замером ветки; при правке описания на ревью перепроверь и прежние утверждения затронутых пунктов.
- Последняя строка — `Задача: <KEY>`.

```
## Что сделано
- `<путь/файл>`: <что изменилось в поведении>.
  - `<метод>`: <деталь>.
- <что сознательно не менялось>.

## Проверки
- <typecheck, линтер> — ок; <тесты: команда или набор> — <N> наборов, <M> тестов, ок.
- `<спека>`: <какие случаи покрыты>.
- Мутации: <N> из <M> краснеют (<какие>).
- Ревью: <роли>, <кругов> — <итог>.

## Отклонения от постановки
1. <что сужено или исключено> — <причина>, <ссылка на решение>.

## Открытые вопросы и замечания
1. Конфликт с открытым #<номер> (<KEY>): <файл> — <что делать вливающемуся вторым>.
2. <решение вне постановки или компромисс>.
3. Не запускались <что> — <почему>.

Задача: <KEY>
```

## Отчёт после пуша

```
Отправлено: <ветка> <старый SHA>...<новый SHA>
- Коммиты: <sha> <название> (по строке на коммит)
- Проверки на <SHA>: <команда — результат>
- PR #<номер>: создан | уже был — <ссылка>; ревьюер <логин>
- Проверки CI: <статус> — <ссылка>
- Не вошло в коммит: нет | <неотслеживаемые файлы>
```
